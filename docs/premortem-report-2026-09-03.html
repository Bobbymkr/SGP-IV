Premortem — Adaptive Traffic Signal Timer

2026-09-03 · Klein-method premortem on the remaining plan (Phases 5 / 6 / T + the deployment path). Frame: it is 6 months from now (≈ March 2027) and the plan has failed. Context brief: docs/premortem-context.md.

Synthesis

Most likelyF1 · The footage never comes

Phase T stays "ready (blocked on footage)" for six months because "authorities provide annotated data" is a verbal commitment with no named owner, no date, and no fallback. The model registry stays empty, device.yaml points at artifacts that don't exist, and OnnxDetector is never run on a real frame.

Most dangerousF3 · Sim-to-real credibility gap

Every headline claim (+76.5% wait reduction on 5-way, queue-error gradient 0.00→1.32) is synthetic-only. The first serious pilot question — "show me this on real footage" — has no answer, and the eval matrix loses its authority in one meeting. (Runner-up: F2 int8 accuracy collapse.)

Hidden assumption

The plan treats synthetic simulation results as sufficient validation for real-world deployment claims.

Revised plan

  1. De-risk the footage dependency now. Send a written data request with a named owner and a delivery date; simultaneously run a footage-independent fallback — execute convert→train→export→int8→registry→eval end-to-end on any small real/public Indian traffic set (or ~500 self-captured frames at one junction) so the pipeline is proven before the real batch lands. → guards F1, F7
  2. Define D6's tolerance as a number. Write "queue_error ≤ X per scenario class" into the master plan / configs/ and enforce it in evals/runner.py regression flagging, so a tier-low breach is machine-detected, not debated. → guards F2, F8
  3. Record a real bench-detect row + one hardware-in-the-loop run. Run make bench-detect on CPU with a frame stream, record it in docs/BENCHMARKS.md, and profile one second machine (even the dev box as "low tier") via profile_device.py to validate tier auto-detection end to end. → guards F4
  4. Buy credibility incrementally. The moment any real clip exists — even unannotated — run a qualitative backtest (OnnxDetector → engine vs fixed-time plan on the same frames) and store the result next to the synthetic scorecard. → guards F3
  5. Anti-rot gates. Add a staleness gate to the Orca pipeline (re-run make eval if the scorecard is older than the last engine commit) and a self-rule: no Orca/graph tooling change in a week without a core/ change in the same week. → guards F5, F9
  6. Reproducibility insurance. Once: fresh clone on a clean VM/second machine, get make verify green from the README alone; fix whatever breaks. → guards F6

Pre-launch checklist

  • C1. Written data request sent — named owner + delivery date; fallback micro-dataset run scheduled if no response in 30 days. prevents F1, detects F1 early
  • C2. D6 queue-error tolerance written as a number and enforced in eval regression flagging. prevents F2 and F8 from going unnoticed
  • C3. bench-detect row recorded in docs/BENCHMARKS.md + one profile_device run on a second machine. prevents F4
  • C4. One real-clip qualitative backtest result stored in docs/. directly counters F3
  • C5. make eval staleness gate wired into Orca pipeline + one fresh-clone make verify green. prevents F5, F6; exposes F9 drift

Failure deep-dives

F1 · Phase T footage deadlock

probability: highimpact: high

The failure story. August 2026: the status board reads "🔶 ready (blocked on footage)". The Colab notebook, converters, and OnnxDetector are finished and dry-run on mock data — but the one thing they wait for, annotated footage from authorities, was a verbal commitment with no owner and no date. Nobody chases it because everything else is green. By March 2027 models/registry/india-yolov8n/ is still empty; device.yaml points at artifacts that don't exist; int8 quantization has never been calibrated on Indian frames; OnnxDetector's real-frame decode path has never executed outside the mock dry-run. A pilot inquiry arrives and the "deploy-anywhere" claim can't be demonstrated even once.

Underlying assumption. An authority will hand over usable annotated footage without a contract, date, or named owner.

Early warning signs. (1) Phase T row in MASTER_PLAN §7 unchanged for >30 days with no chase action logged. (2) No named contact or written data request exists anywhere in docs/ or vault/.

F2 · int8 quantization accuracy collapse

probability: medium-highimpact: high

The failure story. Footage does arrive — late. Training goes well until the notebook's int8 static-quantization step: auto and motorcycle — small, dense, irregular — lose 10+ mAP50 points after calibration on ~200 frames. The low tier (device.yaml: int8, 5 fps, interpolation-only per D6) now feeds systematically undercounted queues into the controller. D6's escape hatch — "hybrid detector if eval shows queue error above tolerance" — can't trigger, because the tolerance was never written down as a number, so nobody agrees a breach happened. The failure is invisible by construction.

Underlying assumption. int8 static quantization holds acceptable accuracy on Indian imagery with a ~200-frame calibration set.

Early warning signs. (1) Per-class mAP50 for auto/motorcycle drops >5–10 pts in the notebook's quantized-vs-fp32 comparison. (2) Eval queue_error for tier-low scenarios exceeds the level that made D6's authors write the hybrid clause.

F3 · Sim-to-real credibility gap

probability: highimpact: high

The failure story. The scorecard is impressive: adaptive cuts average wait 76.5% on 5-way, 31% on 3-way; queue error climbs cleanly with weather severity. But every number comes from the same synthetic engine, synthetic weather (D3), and synthetic discipline presets. Early 2027: a city ATCS program asks for one real-junction result before a pilot. There is none — no backtest on a real clip, no real detector fps, no hardware-in-the-loop run. The honest answer, "it's all simulation," ends the conversation. The project's core claim is discounted exactly when it matters most.

Underlying assumption. Synthetic scenario results transfer to real deployments, or at least persuade real stakeholders.

Early warning signs. (1) Zero real entries in meta/captures.json and zero bench-detect rows in docs/BENCHMARKS.md. (2) Any deployment/pilot conversation stalls at "where is the real-data validation?"

F4 · Device portability claimed, never exercised

probability: mediumimpact: high

The failure story. D5's promise: the same codebase serves a CPU-only box → Jetson via device.yaml alone. The tiers exist on paper; the TensorRT adapter is "pending Phase 5"; active_tier: auto has never run against a real machine. The first real deployment in 2027 is a legacy x86 IPC: the onnxruntime CPU provider delivers 2 fps, not the 5 fps target, because bench-detect was never recorded and MJPEG capture resolution/framerate assumptions were never tested. profile_device.py misclassifies the box, and the ring-buffer pipeline — designed but never stressed — deadlocks under real camera cadence. The portability claim fails at first contact.

Underlying assumption. ONNX tiering plus profile_device.py and config-level tiering suffice without physical hardware-in-the-loop tests.

Early warning signs. (1) docs/BENCHMARKS.md's Detection table still has zero rows. (2) docs/device-tiers.md (Phase 6) still unwritten when the first deployment conversation starts.

F5 · Success-criteria erosion / plan rot

probability: mediumimpact: medium

The failure story. Baseline sim is 57× over target, so Phase 5 feels optional and stays "🔶 partial" forever; Phase 6 "continuous" never produces device-tiers.md. The maintenance rule — update MASTER_PLAN after every phase, BENCHMARKS after every bench run — quietly dies around September 2026 (last updated 2026-08-26). Six months later the plan document no longer reflects reality: the eval matrix hasn't been re-run since engine changes because loop-fast stays green, the change log stopped, and the status board lies. The paper trail that made the project auditable decays.

Underlying assumption. Verification discipline and documentation habits survive after the initial sprint novelty wears off.

Early warning signs. (1) MASTER_PLAN change log and BENCHMARKS rows stop advancing while commits continue. (2) make eval results older than the latest engine commit.

F6 · Single-environment fragility

probability: low-mediumimpact: medium-high

The failure story. The entire loop lives on one Windows box: OneDrive-synced workspace, one venv, one .graph-mem brain, PowerShell scripts (resume.ps1, auto-graph.ps1), a freelm .env pool. A Python minor upgrade breaks a pinned wheel; OneDrive sync conflicts graphify-out/ mid-run; the venv corrupts. Six months in, a full week is lost reconstructing the environment — because the README's setup path was never exercised end-to-end from a fresh clone by anyone, on any machine.

Underlying assumption. The dev-loop environment is stable and reproducible from scratch.

Early warning signs. (1) loop-fast or graphify needs manual repair after any OS/Python update. (2) Git status shows recurring sync conflicts in graphify-out/ or checkpoints/.

F7 · Class-schema mismatch discovered too late

probability: mediumimpact: medium

The failure story. DATASET_SPEC.md v1 locks 6 classes and honestly flags them provisional. When footage finally arrives, the delivered annotations lump tempos and e-rickshaws into "car", and the authority's annotation tool exports a fixed 11-class COCO schema. The "append new ids at END" contract assumes control of an annotation pipeline the project doesn't have. prepare_dataset.py --check rejects 40% of the first batch; retraining is forced, the calibration set is invalidated, and Phase T slips another cycle.

Underlying assumption. Received annotations will map cleanly onto the 6-class contract.

Early warning signs. (1) --check failure rate >10% on the first real batch. (2) Delivered annotation format differs from the requested YOLO layout, or meta/captures.json is absent.

F8 · Eval-matrix false confidence

probability: mediumimpact: medium-high

The failure story. "Eval matrix covers geometry × discipline × weather × incident × tier" gets checked off — 11 scenarios. But incidents are only sensor_failure and lane_block; the documented India taxonomy (autorickshaw_block, cattle_on_road, religious_crowd, political_rally) never became scenarios. Tier is "simulated via degraded confidence/latency" — the real detector never feeds the matrix. And both arms (adaptive and fixed) share the same queue estimator, so the comparison measures scheduling, not perception. Six months on, the matrix "proves" a robustness the real system doesn't have — and the gap surfaces during the pilot, not in CI.

Underlying assumption. Simulated degradation approximates real detector degradation closely enough to validate control quality.

Early warning signs. (1) No scenario consumes a real detection stream or real frames. (2) queue_error is exactly 0.00 in clear/disciplined scenarios — a cleanliness real sensors never produce.

F9 · Meta-work drift while the core freezes

probability: mediumimpact: medium

The failure story. With Phase T blocked, effort flows to what's unblocked and fun: Orca autobuild phases, graph tooling, vault mirrors, the freelm pool. Commits to src/adaptive_traffic/core/ trend toward zero while scripts/ and vault/ flourish. It all feels like progress — the loop is more automated than ever — but the product core (detection on real data) is frozen, and the drift compounds exactly like a wrong-buyer pull: built for the loop, not for the signal.

Underlying assumption. Meta-infrastructure work compounds toward deployment rather than substituting for it.

Early warning signs. (1) 30-day rolling commit share: core/ <20% while scripts//vault/ grow. (2) Orca/graph pipeline gains features in the same weeks Phase T shows no movement.
